# Firebase (with consent) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Any app can turn on Firebase (Remote Config, Analytics, Crashlytics) on Android and iOS
through config plus one DSL line. Data collection waits for consent, which is gathered at first
launch only where the law requires it. Showcase proves this in Debug builds only.

**Architecture:** The rules live in shared Kotlin (KMP):
- typed remote values with fallbacks;
- the consent state;
- the collection policy, i.e. what may be collected when.

The SDKs sit behind small ports:
- **Android:** SDK modules (`:core:consent:google`, `:core:firebase:google`) contribute their Koin
  bindings through the existing `ModuleContributor`/`ServiceLoader` mechanism, and only into the
  build types that enable Firebase.
- **iOS:** Swift targets (`WhitelabelConsent`, `WhitelabelFirebase`) implement the same ports and
  register them with `SharedGraph` before it starts.

Without an SDK, a service runs "off": defaults, and logging only. In Debug, missing config files
switch it to "fake".

**Tech Stack:**
- Kotlin 2.2 KMP, Koin, kotlinx.serialization, `kotlin.test` + AssertK, JUnit5 (Android/build-logic);
- Firebase Android BoM (Remote Config, Analytics, Crashlytics), Google UMP (Android/iOS), the
  `google-services` and Crashlytics Gradle plugins;
- Firebase iOS SDK via SPM, Touchlab CrashKiOS;
- SwiftUI, XcodeGen, XCTest/XCUITest.

**Spec:** [`docs/superpowers/specs/2026-11-12-firebase-and-ads-kmp-design.md`](../specs/2026-11-12-firebase-and-ads-kmp-design.md)
(sections 0–4, 6–8). Parent: `2026-11-10-standalone-app-support-design.md` section 5. The ads plan
follows separately (`feat/ads`).

**Branch:** `feat/firebase` (one PR). If the review gets too big, split it after Task 7 into
`feat/firebase` (shared + Android) and `feat/firebase-ios` (Tasks 8–12). Both keep the build green.

## Global Constraints

- No app identity outside `apps/<name>/` and `ios/<App>/`. Firebase config files are app identity.
- `firebase.enabled` accepts exactly `false` (default), `true`, `debug`. Anything else is a config
  error naming the file and key.
- `true` with a missing config file fails the build on that platform. With `debug`, a missing file
  means the fake Firebase in Debug.
- Release builds of an app with `firebase.enabled=debug` contain no Firebase or UMP classes on
  Android. On iOS they may link the packages but never configure or start them.
- No analytics event or crash report leaves the device before consent is `Resolved`. Events from
  before that are dropped, not queued.
- Analytics and Crashlytics collection is off in Debug unless the Debug-only analytics switch is on.
- The consent form never blocks the splash. It is requested after the first screen appears, once per
  launch.
- Shared features never depend on Firebase, consent or ads. WhitelabelKit never imports Firebase or
  UMP.
- An app without Firebase links none of it: no Gradle plugin applied, no Swift package, no Info.plist
  key beyond `WLFirebase = off`.
- Ports that Swift implements are **callback-based, with no `suspend`**. Swift can't implement a
  Kotlin `suspend` member. Kotlin wraps them with `suspendCancellableCoroutine`.
- Git rules as in `CLAUDE.md`: Conventional Commits, staging by explicit path, `scripts/check.sh`
  green before each push, and `scripts/check-ios.sh` green for iOS tasks.

## Review Focus

1. A remote boolean written as `"TRUE"`, `" 1 "` or `"yes"`. Expected: `"true"`/`"1"` read as true and
   `"false"`/`"0"` as false, trimmed and case-insensitive. Anything else returns the default
   (Task 3).
2. A remote long beyond `Long.MAX_VALUE`, or a decimal where a long is expected. Expected: the
   default, never an exception (Task 3).
3. Consent gathering triggered twice in one launch (first screen plus a resume). Expected: one UMP
   request and at most one form (Task 2).
4. `firebase()` in the DSL while `app.properties` says `false`, or the reverse. Expected: startup
   fails with a message naming the missing piece (Task 6).
5. Showcase release built while `google-services.json` exists locally. Expected: the release APK
   still has no Firebase classes, and its `google-services` processing is skipped
   (Task 7, `verify-apps.sh`).

  sealed interface ConsentState {
      data object Unknown : ConsentState
      data class Resolved(val canRequestAds: Boolean, val analyticsAllowed: Boolean) : ConsentState
      data object Failed : ConsentState
  }
  enum class UmpStatus { UNKNOWN, REQUIRED, NOT_REQUIRED, OBTAINED }
  data class UmpResult(val status: UmpStatus, val canRequestAds: Boolean, val purposeConsents: String?)
  fun consentStateOf(result: UmpResult): ConsentState

  interface ConsentPort {                                      // Swift implements this: callbacks only

      fun privacyOptionsRequired(): Boolean
      fun showPrivacyOptions(onDone: () -> Unit)

      val privacyOptionsRequired: StateFlow<Boolean>

      fun showPrivacyOptions()
  }

  - `NOT_REQUIRED` → `Resolved(canRequestAds, analyticsAllowed = true)`;
  - `REQUIRED` and `UNKNOWN` after a gather (form dismissed) → `Failed`.
  - `gather` calling back `null` → `Failed`.

- Consumes: `RemoteValues` (Task 1), `Consent`/`ConsentState` (Task 2), `Analytics`/`CrashReporter`

- Produces:
  ```kotlin
  interface RemoteConfigSource {                     // Swift implements this: callbacks only
      fun raw(key: String): String?                  // the activated value; null when absent
      fun fetchAndActivate(onDone: (changed: Boolean) -> Unit)   // never throws; false on error
  }
  class SourceRemoteValues(source: RemoteConfigSource, scope: CoroutineScope) : RemoteValues {
      fun start()                                    // one fetchAndActivate in the background; emits changes on true
  }
  data class Collection(val analytics: Boolean, val analyticsStorage: Boolean, val crashes: Boolean)
  fun collectionFor(consent: ConsentState, debugBuild: Boolean, debugAnalytics: Boolean): Collection
  interface CollectionSwitch { fun apply(collection: Collection) }   // Swift implements this
  class ConsentGatedAnalytics(inner: Analytics, consent: StateFlow<ConsentState>) : Analytics
  class ConsentGatedCrashReporter(inner: CrashReporter, consent: StateFlow<ConsentState>) : CrashReporter
  class FakeRemoteConfigSource(values: Map<String, String>) : RemoteConfigSource
  enum class FirebaseMode { OFF, ON, FAKE }
  fun firebaseModule(mode: FirebaseMode, debugBuild: Boolean, debugAnalytics: Boolean): Module
  ```
- `firebaseModule(mode = ON)`:
  - expects `RemoteConfigSource`, `Analytics` (named `"firebase"`), `CrashReporter` (named
    `"firebase"`) and `CollectionSwitch` to be bound by the platform (Tasks 6 and 9);
  - binds `RemoteValues` to `SourceRemoteValues`, `Analytics`/`CrashReporter` to the
    consent-gated wrappers of the named ones, and an eager collector that calls
    `CollectionSwitch.apply(collectionFor(state, …))` on every consent change.
- `FAKE` binds `FakeRemoteConfigSource(mapOf("showcase_remote_note" to "from the fake"))`, plus the
  logging analytics wrapped by the consent gate. `OFF` binds nothing (the Task 1 defaults stay).
- Rules for `collectionFor`:
  - not `Resolved` → all false;
  - `Resolved`: `analytics = crashes = (!debugBuild || debugAnalytics)`, whatever the user chose;
  - `analyticsStorage = analyticsAllowed`.

  So a declined user is still counted, without identifiers. Crash reports are on for any `Resolved`
  state (spec, call 5).
